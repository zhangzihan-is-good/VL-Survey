Coding table guide

What each column means, which values it can contain, and when it applies.

564 systems · 124 columns. Each workbook row describes one modeled system. Several papers may describe the same system.

Before you read: branches and missing values

The columns apply to both virtual models and self-described digital twins. Conditions based on model type, evidence, or the presence of a feature are shown where relevant. A twin label alone does not establish a completed feedback loop.

System identifier

system_id

A stable identifier assigned to one modeled system in the survey. Several papers can describe the same system.

Possible values

A survey identifier beginning S or DS, followed by three digits.

For example S001 or DS001

System name

system_name

The name used to identify the modeled system in this survey.

Possible values

Descriptive text. Values depend on the particular system and article.

For example Name of the modeled system

Survey branch

branch

The branch through which the system entered the survey: virtual models or self-described digital twins. A twin label alone does not show that the system has a completed feedback loop.

Possible values

  • self-described digital twins

    The system belongs to the branch whose own authors use a twin designation; it need not meet the survey criteria for a completed feedback loop.

  • virtual models

    The system belongs to the virtual-model branch of the survey.

Article link

Population of model instances

population_of_models

Whether parameter-varied model instances represent population variability without a one-to-one link to measured individuals. Multiple random runs of one fitted model do not alone qualify.

Possible values

  • no

    A negative coding decision for the stated criterion in the material assessed. It is not a missing value.

  • yes

    The stated criterion is met in the coding assessment.

Different parameter sets must represent population variation. Randomly sampling outputs from one fitted model is not by itself a population of models.

Model type

model_type

The basic way the model produces predictions: mechanistic equations or rules, learning from data, a combination of both, or coordination by LLM agents.

Possible values

  • LLM agent orchestration

    An LLM agent coordinates tools or submodels and passes information among them during operation.

  • data-driven

    A flexible predictive mapping or representation is learned from data.

  • hybrid

    Mechanistic and learned components both contribute to the model predictions or simulated states.

  • mechanistic

    Predictions follow equations or rules based on biological, physical, or chemical knowledge; fitting their parameters does not alone make the model data-driven.

Algorithms used by the model

algorithm_family

Algorithms actually used to produce predictions or simulations in the system. Methods used only for preprocessing, visualization, or comparison are excluded.

Possible values 23 options

Several values may be selected; they are separated by semicolons.

  • Bayesian and simulation-based inference

    Parameters or predictions are inferred probabilistically, including inference based on simulations.

  • Boolean and rule-based models

    States change through Boolean logic or explicit rules.

  • Classical machine learning and statistical models

    Statistical or conventional machine-learning predictors outside the listed deep architectures.

  • Constraint-based model

    Predictions satisfy a defined set of constraints, such as metabolic balance constraints.

  • Diffusion or flow matching

    A generative model learned through diffusion or flow-matching methods.

  • Graph neural network

    A learned network that passes or aggregates information over graph nodes and edges.

  • Joint-embedding predictive architecture

    A model trained to predict one latent representation from another.

  • LLM agent

    An LLM coordinates tools or model components during operation.

  • Large language model

    An LLM directly contributes to prediction or simulation.

  • Neural ODE or neural operator

    A learned continuous-time dynamical model or a learned mapping between functions.

  • Not reported

    The article does not provide this information.

  • Optimal transport

    A method that maps or compares distributions through an optimal-transport objective.

  • Ordinary differential equations

    Time evolution is represented by ordinary differential equations.

  • Other

    Another reported algorithm not represented by the listed families.

  • Other deep network

    A deep neural network outside the separately listed architecture families.

  • Partial differential equations and finite elements

    Spatial fields are represented by partial differential equations or finite-element methods.

  • Particle or stochastic simulation

    A simulation explicitly represents particles or stochastic events.

  • Physics-informed neural network

    A neural network trained with explicit physical or governing-equation constraints.

  • Physiologically based pharmacokinetics and quantitative systems pharmacology

    A physiological or pharmacological compartment/pathway model represents drug disposition or effects.

  • Reinforcement learning

    A policy or decision model learned from a reward objective.

  • Transformer

    A network based on a Transformer architecture.

  • Variational autoencoder and other latent-variable generative models

    A generative model using learned latent variables, including variational autoencoders.

Evidence and comparisons

How predictions were evaluated, which claim was tested, and what alternatives were compared.

Highest task evidence

highest_evidence_level

The strongest evidence reported for any task performed by the system. This can be stronger than the evidence for the paper’s main capability claim.

Possible values

  • E0No comparison with observed data or demonstration only

    A demonstration or simulation without comparison with observed data. Synthetic data from the same model family alone do not establish empirical validation.

  • E1Agreement with construction, calibration, or training data

    Agreement with data already used to construct, fit, calibrate, or train the model.

  • E2Held-out prediction under the same conditions

    Prediction of observations not used for fitting, under the same kinds of conditions.

  • E3Retrospective prediction under unseen conditions

    Prediction for previously untested perturbations, times, contexts, or individuals using data that already existed.

  • E4Prospective wet-lab or clinical validation

    A prediction precedes a newly conducted experiment or new clinical measurement and is evaluated against its outcome. The separate strength field describes how clearly the source reports that timing and the experimental methods.

E0: demonstration only. E1: agreement with data used to build the model. E2: held-out data under the same conditions. E3: existing data from unseen conditions. E4: prediction before newly collected experimental or clinical measurements.

Cross-scale links

How information passes between biological scales and whether those links were tested.

How to read a cross-scale link

Each link records four things: the mechanism, the kinds of endpoints, the direction, and the source and target scales.

Parameter or boundary-condition passing | model-to-model | bottom-up | cell → organ

This example passes information from a cell model to an organ model. Links 1–4 use the same format.

How information is passed
  • Claim only without an implemented interface

    A cross-scale connection is claimed without a demonstrated implemented interface.

  • Parameter or boundary-condition passing

    One component supplies parameters or boundary conditions to another.

  • Representation reuse

    A representation produced at one scale is reused by another component.

  • Joint training or joint solution

    Components at different modeled scales are trained or solved together.

  • LLM agent orchestration

    An LLM agent coordinates information exchange among model components.

What the two ends represent
  • model-to-model

    Both ends compute their own biological states.

  • measurement-to-model

    Observed data enter a model; the data source is not necessarily a modeled scale.

  • model-to-endpoint

    A model output is compared with an endpoint that is not necessarily modeled.

Direction of information flow
  • bottom-up

    Information passes from a lower biological scale to a higher one.

  • top-down

    Information passes from a higher biological scale to a lower one.

  • bidirectional

    Information passes in both directions.

Individualization and feedback

Final individualization category

individualization_level

How the model is connected to a particular physical individual or sample. The category depends on counterpart measurements and completed actions, rather than on a name such as “digital twin”.

Possible values

  • P0Generic model without a specific physical counterpart

    The model represents a class or a generic system, rather than a named individual object or sample.

  • P1 · calibrationOne-time counterpart-specific calibration

    Data from a particular object or sample are used once to fit its parameters, geometry, or initial state.

  • P1 · inputOne-time counterpart-specific input without individual parameter fitting

    A particular object or sample supplies input once, without fitting individual parameters.

  • P2Repeated updating from the same counterpart without a demonstrated complete feedback loop

    New measurements from the same counterpart enter at least twice and change model states or parameters, but a complete model-guided action followed by new data returning to the model is not demonstrated.

  • P3Repeated updating with executed model-guided action and return of post-action counterpart data

    Repeated updating is combined with an action actually taken on that same counterpart and subsequent data returned to the model.

P0 is generic; P1 uses counterpart data once for calibration or input; P2 updates repeatedly; P3 additionally requires an executed action and new data returning from that same counterpart. Replaying existing longitudinal measurements can count as repeated updating.

Uncertainty

Whether the model represents uncertainty, and how this differs from sensitivity analysis.

Broad uncertainty categories

uncertainty_broad_categories

A broad account of uncertainty or variability represented by the model. It includes noise, stochastic processes, and sensitivity to parameters or modeling choices; evaluation-metric confidence intervals alone do not qualify.

Possible values

Several values may be selected; they are separated by semicolons.

  • intrinsic stochasticity

    Randomness is represented as part of the modeled process.

  • measurement-noise model

    Measurement or observation noise is explicitly represented.

  • none

    An explicitly empty set or absent item under the definition of this particular field; consult its description.

  • parameter or prediction uncertainty

    Uncertainty or sensitivity concerns model parameters, outputs, hyperparameters, structure, algorithm choices, or component ablations.

Explicit uncertainty representation

uncertainty_narrow_status

Whether the model explicitly represents uncertainty through a noise model, parameter distribution, stochastic output distribution, or predictive uncertainty. Sensitivity or ablation analysis alone does not qualify.

Possible values

  • no

    A negative coding decision for the stated criterion in the material assessed. It is not a missing value.

  • yes

    The stated criterion is met in the coding assessment.

Confidence intervals for model performance metrics and sensitivity analysis by themselves count as neither explicit model uncertainty nor predictive uncertainty.

Recorded uncertainty methods

uncertainty_narrow_forms

Descriptions of uncertainty methods recorded during assessment. A described method can have been judged insufficient, so use the separate explicit-uncertainty status for the final yes/no decision.

Possible values

Text describing a recorded uncertainty method. Not applicable fills an empty description when the explicit-uncertainty status is no; Not recorded fills an empty description when that status is yes.
